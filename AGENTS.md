# hmpps-external-users-api

Kotlin/Spring Boot WebFlux (reactive, coroutine-based) REST API for managing HMPPS external (auth) users, groups,
roles and email domains. It is being split out of `hmpps-auth` and currently shares that service's Postgres database
(`auth-db`) via R2DBC — there is no JPA/blocking DB access in this codebase.

## Running & testing locally

Tests need a Postgres instance seeded like `auth-db` (currently just needs the `ROLES` table). Start it with:

```
docker stop auth-db && docker rm auth-db && docker-compose -f docker-compose-test.yml up
```

To run the app locally it depends on `hmpps-auth` also running; use the `dev,local-postgres` Spring profile so it
talks to the local Postgres directly instead of through hmpps-auth.

## Build, test, lint

- Build + full verification (what CI runs): `./gradlew assemble check`
- Run all tests: `./gradlew test`
- Run a single test class: `./gradlew test --tests "uk.gov.justice.digital.hmpps.externalusersapi.service.RoleServiceTest"`
- Run a single test method/nested spec: `./gradlew test --tests "uk.gov.justice.digital.hmpps.externalusersapi.resource.RoleControllerTest.CreateRole"`
- Kotlin toolchain is JVM 25 (`kotlin { jvmToolchain(25) }`); use that JDK if running gradle wrapper issues arise.
- Linting/formatting/dependency checks are provided by the `uk.gov.justice.hmpps.gradle-spring-boot` plugin and run
  as part of `check`. `gradle.properties` and the Snyk policy file are generated by this plugin — don't hand-edit the
  warning-banner sections.

## Architecture

Layering is `resource` (WebFlux `@RestController`s) → `service` → `repository` (Spring Data R2DBC) → `repository.entity`.

- All controller/service/repository methods that touch the DB are Kotlin `suspend` functions using R2DBC coroutine
  repositories (see `UserGroupCoroutineRepository`, `UserRoleCoroutineRepository`) — avoid introducing blocking JDBC
  calls or `Mono`/`Flux` return types in new code; follow the existing coroutines style.
- `config/ResourceServerConfiguration` wires JWT auth (via `AuthAwareTokenConverter`) and `@EnableReactiveMethodSecurity`;
  almost every endpoint requires authentication except health/info/swagger/csrf paths.
- `config/AuthenticationFacade` / `security/SecurityUserContext` expose the current authenticated principal; use these
  rather than pulling the `Authentication` out of the reactor context manually.
- `security/MaintainUserCheck` enforces group-based "can this admin maintain that user" rules
  (`UserGroupRelationshipException`) — most user/role/group mutation services call this before acting.
- DB schema: Flyway migrations live under `src/main/resources/db/migration/auth` (original hmpps-auth schema, H2/dev
  friendly) and `db/migration/auth_postgresql` (Postgres-specific follow-up migrations, e.g. auto-generated IDs).
  `db/migration/dev` contains dev-only seed data. New schema changes should go in `auth_postgresql` unless they must
  also apply to the legacy auth schema.
- `EmailDomainService` / `VerifyEmailDomainService` / `config/EmailDomainExclusions` implement an allow/exclude list
  for permitted email domains on user creation — check both when changing email validation behaviour.

## Conventions

- Services are `@Transactional(readOnly = true)` by default at the class level, with individual mutating methods
  marked `@Transactional` explicitly (see `UserService`). Follow this pattern for new services.
- Mutating actions that matter for audit typically emit a `telemetryClient.trackEvent(...)` call with a `username`/`admin`
  map — keep this when adding similar admin actions.
- Tests are split into fast unit tests (`*ControllerTest`, `*ServiceTest`, mocked collaborators via `mockito-kotlin`'s
  `mock()`/`whenever()`/`verify()`, no Spring context) and slower integration tests (`*ControllerIntTest`, extending
  `integration.IntegrationTestBase`, which boots the full app on a random port with WireMock-stubbed hmpps-auth and
  real Postgres).
- Test classes group scenarios using JUnit 5 `@Nested inner class` blocks named after the operation (e.g. `CreateRole`,
  `GetPagedRoles`, `AmendRoleName`) — add new test cases to the matching nested class rather than the top level.
- `JwtAuthHelper` + `IntegrationTestBase.setAuthorisation(user, roles, scopes)` is the standard way integration tests
  set up bearer tokens/authorities for `webTestClient` calls.
